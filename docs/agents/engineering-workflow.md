# 工程工作流

## 变更边界

- 开始前运行 `git status --short`，识别并保留用户已有改动。
- 只修改完成任务所需的文件；遇到重叠改动时先理解再合并，不得擅自回退。
- 优先沿用仓库已有模块、接口和测试方式。新增抽象前，确认它能集中真实复杂度或支持至少两个实际适配器。
- 未经明确授权，不创建或发布 Issue、PR、tag、Release，也不修改远端仓库设置。

## 事实来源

- Maven 项目版本和 Java 依赖以根 `pom.xml` 及各模块 POM 为准；前端版本和依赖以 `frontend/package.json` 与 `frontend/package-lock.json` 为准。
- 支持的 CI/Release 行为以 `.github/workflows/` 和发布契约脚本为准。修改版本或工具链时，同步更新锁文件、CI、README 和变更记录。
- 文档与构建清单冲突时，先以可执行构建配置为准，再修正文档；不要复制文档中的旧版本号继续扩散。

## 安全约束

- 不在代码、配置、日志、测试快照或文档中写入真实凭据、令牌、私钥、个人数据或生产连接信息。
- 不输出环境中的敏感值；示例一律使用明确的占位符。
- 删除 Release、tag、分支、远端资产、数据库或不可恢复的数据前，必须确认准确目标并获得明确授权。
- 涉及认证、授权、文件访问、SQL、命令执行或外部 URL 的改动，应覆盖失败路径和越权路径，不能只验证成功路径。
- 发现疑似漏洞时遵循根目录 `SECURITY.md`，不要在公开 Issue 中披露利用细节。

## TDD 与验证

- 修复缺陷或新增可观察行为时，优先执行红、绿、重构：先用测试稳定复现，再实现最小修复，最后在测试持续通过的前提下整理代码。
- 测试应通过模块公开接口验证行为；避免为了测试而暴露内部实现或大面积 mock 私有细节。
- 无法先写测试时，在交付说明中解释原因，并执行与风险相称的替代验证。
- 后端至少运行受影响 Maven 模块及其依赖的测试；前端按改动运行类型检查、相关 Vitest 和必要的构建检查。
- 文档或发布流程变更应检查链接、命令、版本号和打包内容，不能仅依赖 Markdown 语法正确。
- 交付前再次运行 `git status --short`，明确列出已执行和未执行的验证。

## 本地产物边界

以下内容只属于本地工作区，不得原样提交或整体打包进 Release 安装包；发布白名单明确选择的编译产物除外：

- Maven `target/`、前端 `node_modules/`、`build/`、覆盖率和临时报告；
- `.tmp/`、日志、PID、缓存、IDE 文件和本地下载包；
- H2/MySQL 等运行期数据库、`*.mv.db`、`*.trace.db`、用户上传文件和运行期迁移副本；唯一例外是受 Git 控制的发布种子 `server/src/main/release/bin/h2/yubi.demo.mv.db`；
- 本地配置覆盖、真实密钥、令牌、证书及包含环境信息的诊断文件。

发布打包必须从干净检出构建，并以内容白名单验证安装包。不要直接复制可能被运行过程污染的目录。
