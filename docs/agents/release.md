# Release 工作流

## 发布前提

- Release 必须对应明确版本和提交；版本号、tag、安装包名称、运行时版本信息和变更记录应一致。
- 从干净检出构建，不使用开发目录中遗留的数据库、日志、缓存或历史安装包。
- 默认只从 `main` 发布。发布前要求必要 CI 通过，不以跳过测试的临时构建替代正式产物验证。
- 修改、替换或删除已公开的 tag、Release 或资产属于破坏性操作，执行前必须获得明确授权。

## 产物检查

- 执行后端测试、前端类型检查与测试、完整构建，以及解压后的启动和健康检查。
- 校验安装包内容白名单，确认除受控 `bin/h2/yubi.demo.mv.db` 种子外，不包含其他 `*.mv.db`、任何 `*.trace.db`、日志、PID、凭据、用户文件或开发缓存。
- 安装包必须包含 `LICENSE` 和 `NOTICE`；启动脚本应保留可执行权限。
- 生成并发布 SHA-256 校验值、SBOM 和构建来源证明；条件具备时同时提供签名。
- 在临时目录解压产物进行验证，不在源码资源目录直接启动应用。

## 发布内容

- 更新 `CHANGELOG.md`，说明新增、修复、安全、兼容性变化及已知限制。
- Release Notes 至少包含升级要求、配置变化、下载资产、校验方式和回滚提示。
- Release 页面只声明实际完成验证的安装方式；尚未发布的容器镜像或平台包不得写成可用能力。
- 发布完成后再次核对 tag、资产、摘要、CI 状态和下载说明，并记录验证结果。

## 同版本重发

- 只有在尚无使用者且维护者明确授权时，才可删除并重发同一版本；默认应发布新的补丁版本。
- 先删除旧 Release，完成修复并合入 `main`，再显式把 tag 移到已通过全部门禁的正式提交；工作流不得自行移动 tag。
- 重发必须从 tag 指向的提交重新构建全部资产，不复用本地旧 ZIP；发布后核对 Release 的 tag、提交、SHA-256 和资产列表。
